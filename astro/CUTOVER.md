# Publishing the Astro website

## SH language URL migration

The site owner explicitly chose to replace the previous locale identifier and
language label with **SH** (Serbo-Croatian), using lowercase `sh` in code,
HTML language tags, content filenames and routes. English language switch
buttons show **EN**. The public canonical localized routes are `/sh/`,
`/sh/about/`, `/sh/posts/`, `/sh/search/` and `/sh/privacy/`.

**This is a breaking URL change.** The earlier `/sr/` paths are deliberately
not generated and are not redirected; after the next manually approved Pages
publication, previously shared links using those paths will lead to the site's
existing 404 recovery page. Existing external references must be updated to
their `/sh/` equivalents where needed. The sitemap, language switchers,
canonical metadata, browser tests, and CI route audits target `/sh/`.
No automatic publication is triggered by the code change.

The live site is generated by Astro and hosted on GitHub Pages at
[www.peroniko.xyz](https://www.peroniko.xyz/). Publishing is **manual only**.
Neither merging a PR nor pushing to `master` starts a Pages deployment.

## Publish a new version

1. Merge the intended changes to `master` after reviewing their PR checks, security findings and site behavior. Only committed `master` content is eligible.
2. Open **[Actions → Publish website to GitHub Pages (manual)](https://github.com/Fooftilly/Fooftilly.github.io/actions/workflows/astro-pages-cutover.yml)**.
3. Select **Run workflow**, choose branch **master**, check **Publish the validated master branch to the live website**, and click **Run workflow**.
4. Watch the build and deploy jobs. The build validates and stamps the artifact with the current Git commit, then the deploy job publishes and checks that the live domain serves that **exact commit** and the required routes. A build failure blocks publication; a post-deployment verification failure means the upload may have succeeded but the public result needs investigation.
5. Verify the deployed [homepage](https://www.peroniko.xyz/), [Serbo-Croatian homepage](https://www.peroniko.xyz/sh/), [bookmark composer](https://www.peroniko.xyz/new-bookmark/), search, the [EN tag directory](https://www.peroniko.xyz/bookmarks/tags/) and
   [SH tag directory](https://www.peroniko.xyz/sh/bookmarks/tags/), feeds,
   sitemap, custom domain and [404 page](https://www.peroniko.xyz/404.html). For changes to analytics or comments, also verify consent and third-party network behavior.

The workflow uses a single unchecked-by-default confirmation box. It cannot deploy
from a branch other than `master`. There is **no** repository variable or second
confirmation phrase to set; existing `github-pages` environment protection, if
configured, still applies. GitHub Pages must be configured for GitHub Actions
publication (the original Astro launch used this successfully).

## What the workflow does

It checks out the chosen `master` commit, installs locked dependencies, tests the
source, validates TypeScript, builds `astro/dist/`, checks content and route
parity, bilingual pages, feeds, SEO, internal links, accessibility and browser
behavior. It verifies that internal audit files are absent from the public output,
uploads **only** `astro/dist/`, and deploys that artifact using narrowly scoped
Pages and OIDC permissions in the `github-pages` environment. Before upload,
it writes a public `deploy-revision.txt` containing the source Git commit and
includes it in the private SHA-256 release manifest. After deployment, it
checks the revision at `www.peroniko.xyz` and probes the homepages, bookmark
editor, both localized tag indexes, search, feeds, sitemap and 404. A post-deploy check failure does not
undo a Pages publication; review the deployed URL and Actions logs.

The separate **Astro cutover preflight (no deployment)** workflow can still be
run to download a public-output preview for visual inspection without publishing.

## Rollback

Record the last successful production commit and its GitHub Actions run. If a
later deployment causes problems, create and review a PR that restores the
previously working Astro content/code (for example, by reverting the relevant
changes), verify CI, merge it to `master`, and run **Publish website to GitHub
Pages (manual)** again. A past successful Actions run does not automatically
roll back the live Pages deployment.

The retired Hugo code is available in Git history, not in the current runtime.
No old-Hugo URL compatibility or Hugo build pipeline is maintained.
